# MilestoneGuard — judge questions and evidence-based answers

Current demo: persistent SQLite, simulated INR and optional Stellar **Testnet** XLM. No real-money escrow, legal-compliance certification, trained ghosting model or verified freelancer marketplace is claimed. Commands/results: [verification](docs/VERIFICATION.md); live clicks: [demo](DEMO_GUIDE.md).

1. **How is this different from a task tracker?** Tasks connect to mutually signed scope, private evidence, blocked payments, authorized outcomes and recovery. The browser completion/dispute/recovery journeys demonstrate the connection, not just status labels.
2. **How is it different from a freelancing marketplace?** We focus on accountability after invitation: agreement through completion or recovery. Current discovery is registered-user invitation; bidding, verified matching and commercial marketplace operations are absent.
3. **Does it actually detect ghosting?** It runs configurable server rules on meaningful inactivity, check-ins, deadlines and withdrawal. At 73 demo hours the browser shows timestamped risk without moving money. This is an explainable warning, not proof of fraud or evaluated prediction.
4. **Where is the AI?** Optional Scope Doctor drafting, consented text evidence advice and dispute summaries. Without keys, rules provide a usable fallback. Provider success/error/schema/evidence checks are mocked in tests; live AI is unverified.
5. **Why OpenAI?** An LLM can help turn ambiguous prose into editable scope and human-review questions. Literal phrases, file integrity, dimensions and money are cheaper and more dependable as deterministic checks. No LLM decision binds parties.
6. **What happens when AI is unavailable?** Twelve-second bounded calls, no retries and schema validation fall back to rules. Core agreement, review, payment and recovery work without an API key (`ai.test.ts`).
7. **Can an empty or irrelevant file get paid?** Empty/invalid files are rejected. Agreed objective failures block ordinary acceptance; uncertain subjective work needs human review. There is no automatic semantic quality guarantee. The new UI test rejects invalid files and requires a corrected revision, acceptance and separate payout.
8. **Are you holding real money? Is this escrow?** No. Local INR is simulated; the optional Soroban contract transfers free Testnet XLM. Neither establishes a regulated live escrow service.
9. **How would real payments work?** First obtain provider and qualified legal approval for the exact conditional settlement flow, then implement a provider adapter with signed webhook deduplication, reconciliation and operational controls. No live provider is integrated.
10. **What protects freelancers from unfair clients?** Both sign immutable criteria; amendments need both approvals. Revisions cite agreed criteria and have limits. Workers can submit claims/disputes; overdue client review escalates rather than silently cancelling payment. Browser revision/client-silence tests cover these controls.
11. **What happens when clients ignore submissions?** Server jobs send reminders and escalate after the review window. They do not release payment on a timer. A human-authorized process, and on Testnet the fixed resolver wallet, must determine the outcome.
12. **What happens to the original freelancer's money during recovery?** Earned releases remain unchanged. Unfinished balances remain tied to the original obligation pending authorized settlement. Replacement gets fresh unfunded milestones. The finance regression test keeps completion blocked until the old obligation is settled.
13. **Does the platform automatically find a replacement?** No. A client invites another registered freelancer; availability/acceptance and a new agreement are required. A verified rescue pool and skills matching are future work.
14. **How are duplicate payments prevented?** Transactional writes, unique intent/ledger references, one simulated operation per milestone/kind, balance/state checks and idempotent retries. Six concurrent HTTP requests create one payout. Testnet additionally validates receipts, signatures, sequence use and replay state. Live provider webhooks remain future implementation.
15. **Why Supabase and SQLite? Which is actually used?** SQLite via Node's built-in module, with private local files. No Supabase adapter exists. Current development uses a separate blockchain-dev DB; fresh setup defaults to milestoneguard.sqlite. Managed PostgreSQL/object storage is a future explicitly tested migration.
16. **How are both parties held accountable?** Acknowledged scope, worker activity and immutable evidence, client review deadlines/criterion-linked requests, receipt acknowledgements, claims and audited authorized outcomes. No automatic punishment or fabricated rating follows inactivity.
17. **Does the system cover hiring through completion?** It covers invitation of a registered freelancer, agreement, funding, work, review/payment and recovery. The normal browser journey completes three milestones. Recruitment/KYC, commercial hiring contracts and live settlement are not implemented.
18. **Does it list freelancers and ratings?** It lists registered freelancer choices and recorded activity/performance counts. There are no verified skills/portfolio reviews or invented star ratings. Sparse history is not evidence of reliability.
19. **Can judges see milestones with open disputes?** Yes: Admin controls → Milestones with open disputes shows criteria, private submission versions/checks/hashes, claims and reviewer assignment. The new admin UI test prepares a referenced evidence brief and settles separately.
20. **How are legal orders handled?** Admin records an unverified external reference; a qualified external reviewer's findings may be recorded. The system can only link already confirmed separately authorized settlements within recorded scope. It neither authenticates orders itself nor moves funds because a document claims authority. Fictional UI demonstration and authorization/scope tests cover recordkeeping.
21. **What legal and provider approvals remain?** Provider eligibility and settlement capabilities, applicable regulatory structure, counsel-approved contracts/privacy/IP/disputes/tax/liability, qualified order review, independent security and operational controls. No sign-off is claimed; [readiness checklist](LEGAL_AND_PAYMENT_READINESS.md) records the questions.
22. **What is implemented today?** Authentication/roles, mutual agreements/amendments, private versions, practical objective checks, simulated payments and receipts, configurable monitoring/demo clock, disputes, recovery/replacement, notifications/history and optional AI fallback. Testnet escrow is deployed with recorded network proof. Current test results are in the verification record.
23. **What remains incomplete?** Actual Freighter extension popup verification, live AI success, live INR/provider escrow, production identity/recovery, hosted DB/object storage, malware scanning, email, verified matching, load/independent security testing and legal/operational approvals. Testnet on-chain split settlement is absent.
24. **Why this tech stack?** Next.js/TypeScript shares route/UI types; Node 24 supplies local SQLite; transactions and private disk make the hackathon reproducible without cloud keys. React/custom CSS preserve the working UI. Zod validates inputs/model outputs; Vitest and Playwright verify domain and UI separately. Modern tools alone do not prove reliability or scale.
25. **How does the architecture scale?** Start with one persistent host/relational DB and monitored jobs. History has cursor pagination and indexes; several bootstrap reads remain collection-wide and SQLite writes serialize. Add tested PostgreSQL/private object storage, distributed abuse limits, durable workers/outbox and provider reconciliation before multiple hosts. Measure before splitting services.
26. **What is the practical next step toward launch?** A small controlled pilot after legal/provider/security review, backup restoration drills and monitored operations, using approved sandbox flows first. Gather consented evidence and failure data before investing in matching or predictive risk models. A hackathon pass is not public production approval.
