## Start the application

The current private `.env.local` already uses **separate blockchain development storage**, with the deployed contract configured. From the repository:

```sh
npm ci
npm run db:migrate
npm run db:seed
npm run dev
```

Open `http://localhost:3000`, matching `APP_ORIGIN` exactly. For the optimized server, run `npm run build && npm start`. In another terminal, `npm run jobs:watch` runs accountability checks and resumes pending chain reconciliation. SQLite and private uploads require a persistent single-host Node 24.8+ environment.

For a new checkout, run `npm run setup`, then set these values in the ignored `.env.local` before migrating:

```dotenv
DEMO_MODE=true
APP_ORIGIN=http://localhost:3000
DATABASE_PATH=./data/blockchain-dev.sqlite
UPLOAD_DIR=./data/blockchain-uploads
STELLAR_TESTNET_ENABLED=true
STELLAR_ESCROW_CONTRACT_ID=CDQODC2CCYGKCUKTXXN24BQK4GMKJLUK4QQOWKJP2POD5W3B5NDC27ID
```

Keep the random local secrets generated by setup. No database API key or blockchain signing key belongs in the application environment. Set `STELLAR_TESTNET_ENABLED=false` to run the local demo without wallet/RPC access; existing on-chain records must still be retained.

## Wallet setup

Freighter was **not installed** in the inspected Chrome profile. Actual Freighter popup signing remains an external verification step. Install it from the [official Freighter website](https://www.freighter.app/), unlock/create your own wallet and switch to **Testnet**. Fund conventional `G...` accounts using [Stellar Friendbot](https://developers.stellar.org/docs/build/guides/friendbot). Keep wallet passwords and recovery phrases private.

Use separate client, freelancer and resolver wallets; replacement work needs another freelancer wallet. Independent Chrome profiles are convenient because each has its own application session and selected wallet. The resolver logs into the existing administrator account, but only the escrow's fixed resolver wallet can settle funds. Application admin access alone is insufficient.

After logging in, select **Connect Wallet**, grant access and sign the ownership challenge. The server verifies a five-minute, single-use SEP-10-style challenge against Horizon account signers. It binds the user/session, origin, network, nonce and expiration. This demo supports conventional primary-key accounts; multisig and smart wallets are outside scope. Disconnect preserves wallet history and never changes existing escrow beneficiaries.

## Walkthrough

1. Log in as client, freelancer and administrator in separate profiles. Connect and verify each funded Testnet wallet.
2. As client, choose **New project**, select **Stellar Testnet · XLM only**, choose the freelancer and designated dispute resolver, and define exact XLM amounts and acceptance criteria. Both parties accept the application agreement.
3. As client, select **Create On-Chain Agreement** and authorize in Freighter. Wait for **Transaction Confirmed**. As freelancer, select **Accept On-Chain Agreement** and authorize. Funding requires this confirmed acceptance.
4. As client, select **Fund Milestone On-Chain**, authorize, and wait for confirmation. The confirmed deposit appears in the XLM balance; simulated INR records are unchanged.
5. As freelancer, start work and upload a deliverable using the existing private upload flow. Select **Record Submission Commitment** and authorize. Only the agreement/evidence commitments go on-chain; the file and dispute text remain private.
6. As client, review/download the deliverable, check the existing acceptance checklist and accept it. Separately select **Approve and Release Testnet XLM** and authorize. Wait for confirmation, refresh, and open **View on Stellar Explorer**.
7. For disputes, fund another milestone and enter a reason before **Raise On-Chain Dispute**. Ordinary release is blocked. The designated resolver enters a rationale, chooses release to the original freelancer or refund to the original client, and authorizes **Testnet Settlement**. Split settlement is intentionally not implemented on-chain.
8. For recovery, use existing inactivity/intervention/recovery controls. Invite a replacement and accept a fresh agreement. Create and fund a **new escrow** for fresh milestone IDs. The original escrow remains payable/refundable only to its original parties through its explicit dispute process. The demo clock never changes Stellar time or authorizes a transfer.

The contract enforces participant authorization, fixed beneficiaries, funding limits, exact accounting, submission commitments, dispute blocking, single settlement and no unrestricted admin withdrawal. AI remains advisory. Acceptance in the application alone never signs or releases tokens.

Transactions from one wallet are serialized across tabs/projects to protect Stellar account sequence numbers. Wait for confirmation or reconcile the pending intent before starting another wallet operation. Escrow creation requires the current active mutual agreement; pending amendments cannot freeze stale terms on-chain.

## Pending operations and retained state

An intent is committed in SQLite before RPC preparation. The wallet signs the exact prepared envelope; submission is only pending until a successful network receipt, expected contract event and matching contract state are verified. Confirmations/events are deduplicated. Refreshing or restarting preserves the intent and transaction hash. Use **Resume Wallet Approval** for a valid unsigned intent or **Reconcile** for an uncertain submitted transaction. The background worker performs the same reconciliation. Never blindly create another payment when confirmation is uncertain.

Expiry alone is insufficient to unlock an uncertain payment: retained RPC history must cover the intent through its deadline and prove no execution. Otherwise it remains `RECONCILIATION_REQUIRED`. Financial read-model validation and application run under one SQLite write lock to prevent concurrent reconciliation from regressing confirmed balances. The disposable Testnet deployment identity was removed after deployment; the application has no signing-key configuration.

The original demo was checkpointed at Git tag `codex/pre-stellar-20261014`. Its SQLite backup, private uploads and previous environment are in ignored `data/backups/pre-blockchain-20261014T044216Z/`. The original database and uploaded files remain at their original paths. Never overwrite current chain storage to restore the local demo: stop the server and select the original database/upload paths with the feature disabled, or use another separate local database.

**Reset is blocked whenever any escrow history exists**, including settled history. Chain state cannot be undone by deleting SQLite. Preserve the SQLite database, uploads and configuration together; restore them together if needed. Testnet resets, RPC receipt retention and Soroban storage TTL can require operator recovery; a general historical indexer and archived-state restoration UI are outside this demo.

The additive versioned migration creates wallet/challenge, escrow/milestone, intent/confirmation, event and synchronization tables. Old simulated ledger entries are unchanged. To preserve the existing strict integer schema, legacy chain-project `budget` fields are nonfinancial tracking weights and legacy funded/paid/refunded fields stay zero. **Only `budgetAtomic`/`amountAtomic` and `chain_milestones` decimal strings represent XLM.** UI displays and aggregates use these fields exclusively for Testnet projects.
